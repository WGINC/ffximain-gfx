## 1. The gate now gives callees only values they can really produce

Several FAILs were not translation errors. A gate stub (a stubbed callee) answered with values the
real callee never returns, so two correct programs diverged.

- **Return kinds (`ret_kinds.py`).** A forward dataflow over each function's code classifies its EAX at every `ret`:
  - `bool`: EAX is exactly 0 or 1 (975 functions);
  - `lowbool`: AL is 0 or 1 and the upper bits are left over (1,780 functions);
  - otherwise unknown.

  A stub then answers within that range. Example: `CXiActor_IsModelMissingOrFlag2000` is typed `BOOL`.
  The original tests `al == 1` and the translation tests `!= 0`. Both are right for 0/1, and only the
  gate's random 0x28 told them apart.
- **x87 returns (`fp_callsites.py`).** A stub for a float-returning callee now pushes a value onto the x87 stack. It does so only at calls where the original caller reads it:
  - the next x87 instruction on every path reads ST0;
  - or the caller returns it as its own float result.

  Before this, no stub pushed anything, so a caller that pops a float result popped an empty stack.
- **`fpret.py` corrected.** It now handles:
  - `fpatan`/`fyl2x` (pop one) and `fsincos`/`fptan`/`fxtract` (push one);
  - x87 consumers: functions whose first x87 instruction pops a value they were given, i.e. MSVC
    `__ftol` and two helpers.

  It also records `none` for functions proven to return with an empty x87 stack. 85 functions IDA typed
  as returning a float are proven `none`. They are now translated and gated as `void`. Example:
  `sub_10282A30` converts its float with `__ftol` and returns nothing on the x87 stack.
- **A trampoline bug avoided.** Unicorn caches translated code, so the stub's return trampoline is written once and never patched per call.

## 2. Translator repairs (`hx2cpp.py`)

Each repair is a rule, not a per-function edit, and applies wherever the pattern occurs:

| Rule | What Hex-Rays does | Fixed (examples) |
|---|---|---|
| Exact float constants (`fpconst.py`) | prints a single-precision constant as a short decimal, so in C++ it becomes a different double | `GetWidth/Height/DepthScale`, `GetWalkSpeed` |
| x87 status word | splits `fcom; fnstsw ax` into `c0/c2/c3` but leaves the status word unassigned | `CXiSkeletonActor_OnMove`, `Init`, `OcclusionClip`, `ZoneMap_DrawMeshById` |
| Unconsumed float callees | declares a callee `float` that the caller never reads, so GCC pops a value the original leaves | `Camera_ApplyViewProjection` |
| Signed `_DWORD` | `_DWORD` has no sign in Hex-Rays: comparisons and `/`, `%` take the other operand's sign, and unsigned is written `2u` | cursor clamp `sub_10124640`, `sub_10281DB0`, `sub_102214D0`, `sqgxVertexShaderCreate` |
| Exact stack frame | splits one stack array into several variables and writes across them through a pointer | `Actor_DrawWorldText`, `sub_10086900` |
| In-place buffers | the IDB types a global buffer as a pointer: `qmemcpy(&G, ...)` then `qmemcpy(..., G, ...)` | `sub_1011AA40`, `sub_10162010` (the viewport copies) |
| Type parsing | `void (*)()`, `__noreturn`, Windows pointer typedefs, a global named like a parameter (`::self`) | the last 3 compile failures: **712 of 712 now compile** |

## 3. Hand corrections as data (`data/hx_patches/`)

Some output cannot be repaired by a rule. Example: in `sub_10283420` Hex-Rays took the arguments pushed
before a shared `SetRenderState` call for stack variables overlapping the material struct.

- A patch is the exact snippet and its replacement, with the reason and the disassembly evidence.
- It is applied only while the export's text has the same SHA-1. A re-export after the IDB is fixed
  reports the patch as stale and never applies it silently.
- `hx2cpp.py` and `hx2clean.py` both apply patches.

## 9. Night round: the regression, the dump, and the IDA SP errors

Reproduced first: the facts read from the DLL (`run.sh facts`) came out byte-identical, so the attached DLL
is the analysed build. The fuzz gate gave the recorded 680 / 30 / 2 exactly.

**`Dancer_InitDevice`: traced and fixed.**
- **Cause:** Hex-Rays declared `GetDesc`'s 32-byte `D3DSURFACE_DESC` output as `_BYTE v8[24]`, followed by
  `unsigned int v9` and `int v10` (Width and Height). Nothing writes v9 and v10 except `GetDesc` through
  the array.
- **Why it showed up now:** since `60b62b3` the fake getters really fill their outputs. The original read
  Width = 2 and called `sub_10281830(2, 2, ...)`; under GCC's layout v9 and v10 stayed 0.
- **Fix:** a new rule in `hx2cpp.py`, `filled_past_array`, a fourth sign for `exact_frame`: an address-taken
  array directly followed by a local that is read but never assigned.
- **Result:** the rule changes 17 translations. All 17 were re-gated: `Dancer_InitDevice` now passes, and
  the others keep their verdict.

**Live gate on the 7 Sep dump.**
- `build_map.py` maps the dump's 5 Aug build to the analysed 3 Sep build: 18,436 functions matched (2,341
  more by nearest) and 15,115 globals.
- `live_state.py` turns that into the gate's live inputs.
- **Result:** 659 PASS, 51 INCONCLUSIVE, 2 FAIL (OnMove and DrawProjectedShadow); before this round it was
  658 / 51 / 3.

**Clean tree:** regenerated from the current pipeline, it builds all 181 files, and all 681 functions pass
the gate as built.

**The two FAILs left: real stack depth, measured.**
- `pipeline/real_sp.py` runs each original over the gate's trials, live inputs included, and records ESP
  at every executed instruction.
- It covers all 712 functions: 28,708 instructions in `data/real_sp.json`. One function,
  `sub_1017B510`, reaches 3 instructions at two depths; they are left out.
- **OnMove:** the measurement confirms both points already in `ida_sp_fixes.json`.
- **DrawProjectedShadow:** the depth is 0x134 after `SetVertexShader` (0x101851B4), which pops 8 of the 12
  bytes pushed before it. `stack_depth.py` assumed 12 there, as IDA probably does. The `this` that
  Hex-Rays reads 12 bytes off (`hx_patches/0x10184FE0.json` papers over two of those reads) comes from
  here.
- **Candidates elsewhere:** 51 indirect calls in 40 functions pop a different amount than was pushed just
  before them. Most are arguments MSVC pushes early for a later call, which IDA gets right from the D3D
  prototypes, so they are candidates, not errors.

**IDA fix: `ida/ffxi_ida_fix.py`** (self-contained, built by `pipeline/make_ida_fix.py`). It does not apply hand-picked corrections. It compares IDA's
SP (`get_spd`) with the measured depth at every recorded instruction:
- at each call where IDA's SP change differs from the measured one, it sets a user SP change point there
  and re-analyses;
- it repeats until IDA agrees, with a sign check, because the stored value's convention is not settled:
  the older `apply_sp()` stores `-delta`;
- then it re-exports.

That covers both FAILs, and every other function where IDA's SP is wrong, without a separate sweep.

**Ghidra** (11.4.2, headless, about 4 minutes for the import and analysis) decompiles both functions. Its
output is not usable here: it lost OnMove's `this` (`uint FUN()`), mistyped values (`(float)piVar`), and
neither function compiles. The IDA route stands.

## 10. First IDA run (3 Oct): what it showed

The first `ffxi_ida_fix.py` run applied 185 names, 7 prototypes and the viewport types, set SP points in 10
functions, and re-exported. The pipeline on that export:
- `CXiSkeletonActor_OnMove` passes, fuzz and live;
- `CTsZoneMap_DrawProjectedShadow` passes, fuzz and live;
- three functions that did not translate before now pass: `CDx_CreateRampTexture1x16`,
  `sqgxTextureCreateFromImage` and `sub_1028AB50`.

It also exposed three mistakes of mine, all fixed for the second run:

1. **10 of the 16 SP points were wrong.** The "real" depth came from the emulator, and at fake COM
   objects and stubs, the pop is the gate model's, not the game's.
   - The object at CDx+0x90 got the generic `IDirect3DResource8` fake. Its slot 8 is `GetPriority`,
     which pops 4; the real `GetDesc` pops 8.
   - `D3DXMatrixMultiply` was stubbed as cdecl.
   - Fix: `real_sp.py` records a call's effect only when it comes from real code, or from a fake whose
     interface the gate knows for certain. The second run removes the bad points
     (`data/ida_sp_revert.json`).
2. **The D3DX CPU-dispatch thunks.**
   - `D3DXMatrixMultiply` (0x102D6F03) and `D3DXMatrixTranspose` (0x102D714C) are `jmp [table]` thunks.
     The table is filled at startup from a default copy (0x103CC4F8) or with CPU-specific versions.
   - IDA typed the first `__cdecl` and the second with one argument, so Hex-Rays named every later
     stack slot 12 bytes off in five ZoneMap functions.
   - The gate stubbed them the same way, so the *original* ran with a wrong stack. That is why three of
     them were INCONCLUSIVE.
   - `purges.py` now resolves all 58 thunks to their default implementation's `ret N`. Stubs and
     translation use it, and the prototypes are in `type_fixes.json`.
   - The three now return in the original and FAIL in the reconstruction, until IDA has the
     prototypes.
3. **Hex-Rays takes an untyped indirect call's arguments from the pushes before it, not from IDA's SP.**
   - `CXiSkeletonActor_GetNamePos`/`GetArrowPos` passed only because the gate's stubs were built from the
     same wrong prototypes. Slot 0xB4 really takes no stack argument; slot 0x1C4 takes two.
   - `Gfx_AssembleVertexShader` and `sub_101771B0` give `ID3DXBuffer::GetBufferPointer` the next call's
     arguments. They passed only while the buffer pointer was uninitialised, so the original crashed
     first.
   - The gate stubs now write a fake object into `I...**` outputs, so both FAIL, correctly.
   - The second run forces the call type at such calls (46 candidates), verified by decompiling.

Also from the re-export:
- `D3DVIEWPORT8` and `DNameNode` declarations were added to the translator headers.
- `sub_102D538A` is classed as D3DX library code by address.
- `sub_10178250` is typed `void`: its only caller overwrites EAX.
- `exact_frame` now also covers an address-taken *scalar* followed by unnamed frame space. In the
  re-export, `Dancer_InitDevice`'s `GetDesc` output became `int v8`, 8 unnamed bytes, then `v9[272]`.

## 11. Definitive facts only (3 Oct)

The owner's rule, now in `CLAUDE.md`: **do not guess, do not assume.** Every fact the pipeline uses must
come from a source that settles it, and where none does, the pipeline says so instead of picking the value
that works.

### Where the errors came from

Almost every error since the start had one root: the binary does not record how much an indirect call pops
or what type a value has, so IDA guessed (its stack pointer, Hex-Rays' argument counts, `_DWORD` with no
sign) and so did the gate (pop counts by counting pushes, then searching for a count that "worked"). Each
wrong guess surfaced somewhere else: a stack slot with two names, a call with the next call's arguments, a
loop compare that went unsigned, a FAIL that was the gate's own model.

### The definitive sources

| Source | What it settles | How it is checked |
|---|---|---|
| `purges.py` (existing) | a direct callee's `ret N` | the code itself |
| `sp_solve.py` (new) | each unknown call's pop, from the caller's stack balance: equal depth wherever paths meet, zero at every `ret`; exact rational elimination, a value only where the equations pin it | `--selftest` hides all 20002 known `ret N` of direct calls and solves them back: 20001 right; the one miss (a CRT exit routine that returns only when a flag argument is set) is in a function the per-function check rejects, so 0 wrong values reach the output. 0 disagreements with the 192 measured pops and with all 186 import counts it can solve |
| `vcall_resolve.py` (new) | virtual calls on `this` whose every possible callee is proven | 944 vtables (no RTTI for game classes); an object running method F can only have a vtable holding F, or what F's direct callers pass, else (address taken anywhere else) it is unknown. 531 calls settled; 0 disagreements with the solver (311) or the measured pops (81); 183 are new facts |
| ECX use (in `vcall_resolve.py`) | whether a function reads its entry ECX (`this`) | partial registers tracked, `or ecx, -1` / `xor ecx, ecx` are writes, `push ecx` (MSVC also reserves stack with it) is undecided. Agrees with 1151 of 1152 IDB `__thiscall` declarations; shows 10 IDB `__stdcall` declarations wrong, each with the instruction (`mov edx, ecx`, `add ecx, 178h`, ...) |
| `real_sp.py` (existing) | pops measured by running real game code | trusted calls only |
| IDB-declared call types | COM calls through `lpVtbl` typed from the D3D8 header (1814 in the export) | the next re-export marks each call `typed` or `cast`; only `typed` counts |

`callsite_audit.py` puts them side by side for every indirect call in the graphics code: 2662 calls, 1933
definitive, **0 conflicts**, 729 with no source yet (591 of them COM style, which the typed calls of the
next export should cover).

Two rules I had built into the solver were assumptions, found by its self-test and removed: a tail `jmp`
does not always leave at depth 0 (0x102BCE07 jumps into shared CRT code at depth 104), and a switch table's
length is the bound in front of it (`cmp r, N; ja`), not "while the entries look like code".

### The gate

- Pop counts come only from the sources above (`site_pops`). With none, the trial stops as **UNRESOLVED**
  and names the call site. The push-counting fallback and the search for a count that "works" are gone.
- Windows calls the game makes on its way are answered from what Win32 documents, the same on both sides
  and still compared: the process heap (`HeapAlloc` from the gate's per-run allocator), critical sections,
  thread-local storage, `SetLastError`/`GetLastError`, a created file's position. Where Win32 documents
  several outcomes (`WaitForSingleObject`, `CloseHandle`, `CreateFileA`), the outcome is an input drawn
  from that set, like any fuzzed input.
- The emulator now has a thread information block at FS (a flat GDT, as Windows has it), so MSVC's SEH
  prologue (`mov eax, fs:[0]`) runs.
- The reconstruction gets ten times the original's instruction budget: `ComputeMorphHandle` failed one
  trial only because its compiled code takes more instructions for the same work (with a larger limit both
  return the same result).

Full fuzz gate under these rules (`def1`): 698 PASS, 12 UNRESOLVED (each naming its call sites), 3 FAIL,
1 INCONCLUSIVE; 15 former INCONCLUSIVEs pass.

### What is left, and why

  carries IDA's SP) will show whether that clears it.

  read EAX, so it cannot be shown that no caller uses the value. Documented, not hidden.

  unknown callees (its atexit callbacks) keep EBX, or full stack-slot tracking.
