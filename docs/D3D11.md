# The Direct3D 11 renderer: the scheme

Goal 2 of docs/ROADMAP.md, worked out from what is now measured. Every fact names its source; what is not known is
said to be not known. This is a plan, not a decision.

## 1. What decides the design

**The machine** (the owner, and the kit's environment log; docs/HISTORY.md, 6 Oct):
- An M5 MacBook Pro running Windows 11 on ARM in Parallels.
- pol.exe is a 32-bit x86 process, so all of its code is emulated: the game, dgVoodoo's d3d8.dll (2.8.2), and the
  D3D11 runtime and Parallels' display driver prl_umdd10.dll that dgVoodoo calls. The kit logged every graphics
  module as PE machine x86, none as ARM64 or CHPE.
- The CPUID vendor is "Virtual CPU", with SSE through SSE4.2 and no AVX.
- Windows' own d3d8.dll crashes the game on this machine. dgVoodoo's D3D12 output stretches and flickers textures.
  dgVoodoo's D3D11 output is the one working path (ROADMAP, "Concluded").

**Where a frame goes**, in Port Jeuno's plaza (HISTORY.md, runs 3736, 6156 and session 5; about 71 ms a frame
without speedfix, 31 ms with every lever on):

| Work | Share or cost | Source |
|---|---|---|
| Occlusion readback stall | 19.5% (LockRect, 0x1006C91C) | sampler, run 6156 |
| Character draws | 16%; 1,586 DrawIndexedPrimitive a frame, all from SkinAndDrawV2 | sampler and profile |
| CPU skinning | 13.3% (x87 loop); sse_skinning measured −14.5 ms | sampler; lever A/B |
| Skinning buffer Lock / Unlock | 7.6% | sampler |
| Text and UI quads | 10.3%; 885 DrawPrimitiveUP a frame | sampler and profile |
| Samples in memory of no module | 62 to 70% of the render thread's samples | sampler, runs 6156 and 11952 |

The last row is not explained. The samples have game return addresses under them, so the thread was in code
called from the game that no loaded module holds: plausibly the emulator's translated code for dgVoodoo, the D3D11
runtime and the driver. That is not established, and how much of the frame is the emulation of those layers,
rather than their work, is not known. It is the one number that decides between the designs below (section 3).

**What the speedfix levers already showed** (HISTORY.md, session 5): fewer calls into the D3D8 layer pay off on this
machine. batch_up_draws with lazy_state saved 8.2 ms, and all the levers together halved the frame (71 to 34 ms,
session 1). What one call into dgVoodoo costs is not measured. Run 3736's fit of frame time against setter calls
(1.48 us a call, r = 0.970) is a correlation over one session's scenes, not a measurement. A renderer of our own
issues far fewer calls; how much that saves per call is phase 0's question.

## 2. What the game asks of Direct3D 8 (the scope)

Our own device implements this subset, not the whole interface:
- **As data:** `data/d3d8_scope.json` (pipeline/d3d8_scope.py, 14 Oct). It keeps its sources apart:
  - the static map: 62 methods on 7 interfaces, plus 27 sites whose interface is not established, listed by slot;
  - the owner's traces 6080 and 5180 (34 frames): 33 methods, 25 render states and 35 stage states with the values
    set, 6 FVF codes, 281 shader handles, strips and lists only;
  - five resource logs: every creation's usage, format, pool and FVF;
  - the profiles' calls per frame.
  The device's coverage list is built from it. What the runs did not reach is only in the static part.
- **Methods:** 59 distinct methods at 1,633 call sites (data/render_map.json, static and observed). By site count:
  SetRenderState 636, SetTextureStageState 600, SetTexture 87, SetVertexShader 63, LightEnable 47, SetStreamSource
  22, CreateVertexBuffer 17, SetTransform 16, then fewer. The full list is in that file.
- **Draws:** 12 sites in all: the three CDx wrappers (three sites each, two of them for the stereo second eye), and
  sqgxDlistDraw and sub_1028AB50 (RENDERER.md section 1).
- **Programmable shaders:** the game's code holds 5 vertex shaders (vs.1.1, 19 to 45 lines) and 1 pixel shader
  (ps.1.1, 9 lines), built by one function, 0x10178250, each in two variants (runs/shaders/,
  data/shader_catalogue.json). **None was ever created in the owner's sessions.** Of the 2,253 vertex shaders the
  kit captured (xikit_vshader_*.bin, sessions of 6 Oct to 13 Oct), every one has no function tokens: a declaration
  only. No pixel shader was created in any resource log.
  - 0x10178250 is called from one branch of 0x10178B30, a virtual method (vtable entry 0x10336768) that also calls
    Zone_RenderEnvironment. Which zone or state takes that branch is not established.
  - So every draw seen so far is fixed-function. The port needs no shader translation for what has been observed.
- **Fixed function:** 56 render states and 15 texture-stage state types (RENDERER.md section 1), and the FVF codes
  XYZRHW|DIFFUSE|TEX1, XYZ|DIFFUSE|TEX1, XYZRHW|DIFFUSE, XYZ|DIFFUSE, XYZ|NORMAL|DIFFUSE|TEX1, XYZ and XYZB1.
  Fixed-function vertex shaders come from declarations alone. The 3 distinct ones (run 2's captures):
  - stream 0 position, stream 1 normal, stream 2 texcoord (SkinAndDrawV2's three streams, strides 12, 12, 8);
  - stream 0 position, stream 1 normal, diffuse, texcoord;
  - one stream: position, normal, diffuse, texcoord.
  XYZ and XYZB1 are in the static list only; the traces show the 6 FVF codes above them and no XYZB1.
  - Lighting: up to 8 lights. SetLight is among the most frequent setters (3,925 a frame from one site in run 6080's trace).
  - Fog, alpha test, TEXTUREFACTOR, and the texture-stage combiners.
  - A two-pass stencil shadow volume (sqsnShadowVolumeSetPass).
- **Textures** (both sessions' resource logs): 3,831 DXT3 and 82 DXT1 in the managed pool, which map directly to
  D3D11 BC2 and BC1. A8R8G8B8 in both pools. 12 cube textures. Render targets: the scene's own target
  (3024 x 1898 in run 6080), 256-sized and smaller targets, and one CreateRenderTarget.
  - SetPaletteEntries and SetCurrentTexturePalette have call sites, but neither session created a P8 texture. D3D11
    has no palettes; if one ever appears, it is expanded on upload.
- **Locks:** vertex buffers locked with DISCARD every frame for skinning (SkinAndDrawV2, with a Sleep(0) retry on
  failure), managed textures, and LockRect of a render-target surface for the occlusion readback (the stall).
- **State blocks** (Begin/End/Apply/Create/Delete), gamma ramp, TestCooperativeLevel and Reset.

## 3. The designs

**A. Our own d3d8.dll on D3D11, in the game's process (x86).** It takes dgVoodoo's place, implementing the subset
above. It knows the game, so it can drop and merge what a general wrapper must keep:
- render states into D3D11 state objects, cached by value;
- the fixed-function pipeline as generated shaders, keyed by the state that matters, compiled once and cached on
  disk;
- small draws merged on the CPU and sent as few draws. A ring buffer written with NOOVERWRITE for every small draw
  is not the way on this machine: probe11 measured 4.7 us a call from x86 (2.8 us from ARM64). speedfix's up_ring,
  which did that through dgVoodoo, was slower and was reverted (HISTORY.md, run 7388);
- the occlusion readback as an asynchronous query, answered from the last frame's result (ROADMAP P3).

Every call still runs emulated, but it is ours, and there are far fewer of them.

**A2. A with a second thread.** The game's calls are recorded into a command ring and return at once. A worker
thread of the same process issues them to D3D11. On a machine with many cores, the emulated D3D11 runtime and driver
then run beside the game, not inside its frame. Only what needs an answer waits for the worker: a Lock of a buffer
the GPU is reading, a readback, a Get of state the device alone knows. This is the "splitting threads, ring buffer"
idea. speedfix could not do it, because every D3D8 call waits for the one before it; a device of our own decides
that itself.

**B. A native ARM64 renderer process.** The same command ring, in shared memory, read by a separate ARM64 process
that runs D3D11 natively: no emulation of the runtime or the driver.
- It needs the renderer process to present into the game's window, or to share its output with it. Whether DXGI on
  this setup allows a swap chain on another process's window, or a shared texture across the two, is not known.
- ARM64 Windows code builds here with zig cc (PyPI `ziglang`); llvm-mingw cannot be fetched (GitHub is outside
  this container's egress policy).

**Recommendation:** build A with the command ring from the start: record in the D3D8 entry points, execute in one
function. A2 is then a matter of where that function runs, and B of which process runs it. Section 4's phase 0
measurement chooses between them, before anything is built.

**Game-aware paths** (SDK hooks into the same device), in the order the plaza's numbers give:
1. **Characters:** skin on the GPU. SkinAndDrawV2's bone matrices go into a constant buffer, and its strips into
   one index list per model, built once. That removes Model_SkinVerticesCpu (13.3%), the per-frame buffer locks
   (7.6%) and most of the 1,586 draws. The measured bounds for draws, from 1,620:
   - 510 when every part shares one buffer and repeated light and transform values do not count (session 2,
     merge_potential.py);
   - 764 when each model's strips are only regrouped by state, lights and transform, with no shared buffer, but only
     for parts drawn without alpha blending (HISTORY.md);
   - 1,525 when strips are merged only where they already stand.
2. **Occlusion:** asynchronous queries, a frame late (19.5% in run 6156).
3. **Text and UI:** one buffer and one draw per texture and state (10.3%).
4. **Zone mesh** (task 16): static buffers grouped by texture at load. In run 6080's trace: 3,851 draws a
   frame from 371 buffers and 17 textures. In the plaza: 45 draws.

## 4. Phases

**Phase 0: measure what decides the design (on the owner's machine).** Built: kit/d3d11probe (`run_phase0.bat` runs
all of it; `phase0_report.py` sets the results side by side). Two runs, 6 Oct (phase0_20261006_124338, phase0_20261006_131825):
- D3D11 runs on the Parallels Display Adapter (WDDM) at feature level 11_0, from x86 and from ARM64. BC1/BC2 and
  every format the game uses are supported. d3dcompiler_47 is present. No driver command lists or concurrent creates.
- The plaza-shaped frame (1,600 character draws, 900 UI draws, as D3D8 issues them), time to submit:

  | Path | Run 1 | Run 2 |
  |---|---|---|
  | D3D11 from x86 (median) | 7.78 ms | 8.91 ms |
  | D3D11 from ARM64 (median) | 6.91 ms | 8.66 ms |
  | D3D8 through dgVoodoo, from x86 (mean) | not usable | 7.28 ms |

  So x86 emulation costs this frame 1.13 times (run 1) and 1.03 times (run 2) native. Through dgVoodoo the same
  frame costs no more than through D3D11 directly. D3D8 has no event query, so its time has no GPU wait; D3D11's with
  the GPU wait was 0.1 ms more.
- The same triangles in 33 draws: 0.14 to 0.17 ms through D3D11 from either architecture, and 0.26 ms (mean)
  through dgVoodoo. That is 28 times (dgVoodoo), 51 and 64 times (D3D11, ARM64 and x86) less than as 2,500 draws.
- Per call, the cost of a small draw depends on how many a frame holds: DrawIndexed cost 219 ns at 20,000 a frame
  (run 1) and 906 ns at 200,000 (run 2), on both architectures. So per-call figures from different runs are not
  comparable; the frame figures are. Within run 2 (200,000 calls each): x86/ARM64 0.94 to 1.15 per call; dgVoodoo's
  setters 14 to 115 ns against D3D11's 17 to 101 ns.
- Small dynamic draws: dgVoodoo's DrawPrimitiveUP took 157.5 ns a call, while a D3D11 dynamic-buffer Map with
  NOOVERWRITE plus Draw took 2.8 to 4.7 us. How dgVoodoo makes its UP draws that cheap is not known; a
  NOOVERWRITE Map per small draw is not the way on this machine.
- Every time probe8 measured is a whole multiple of about 2.864 ms (e.g. 71.6 ns x 200,000 calls = 14.32 ms = 5 x
  2.864). Its clock is not the cause: QueryPerformanceCounter's step there is 0.042 us, before and after the device
  is made. So the D3D8 calls themselves end on a ~2.86 ms grid, presumably by waiting; why is not known. Over 200,000
  calls that grid is at most about 14 ns a call, and frame means are not affected by it.
- Cross-process: a child process's swap chain on the parent's window was seen there in both runs and both
  directions. A legacy shared texture opened and was written by the child without error, but the parent never saw
  the written colour; why is not known.

What this says about the designs:
- Native ARM64 (design B) would gain 1.03 to 1.13 times on this frame. Presenting from another process works.
- Replacing dgVoodoo with our own D3D11 device (design A) shows no per-call gain in these measurements: dgVoodoo's
  frame was 7.28 ms against D3D11's 8.66 to 8.91 ms.
- The gain on every path is fewer draws: 28 to 64 times less submit time for the same triangles, and the 33-draw
  frame costs 0.26 ms even through dgVoodoo. Draw merging can therefore be had through the existing D3D8 path, in
  forks of the hot draw functions, without the port.
- What only a newer API offers is in what D3D8 lacks: asynchronous occlusion queries (the readback stall: 19.5% of
  the render thread in run 6156) and freer shaders for skinning on the GPU. Those, not per-call cost, are the case
  for the port, and they are not measured here.
- This is a synthetic frame. The game's frames are 30 to 70 ms with about 3,000 draws, so most of a game frame is
  not draw submission of this kind (skinning, locks, readbacks and the game's own code; HISTORY.md, the samplers).

**Phase 0, run of 13 Oct (HISTORY.md, "13 Oct runs").**
- dgVoodoo's caps on the owner's machine:
  - vertex shader 1.1 with 256 constants, pixel shader 1.4;
  - indexed vertex blending (4 matrices, index up to 255).
  - kit/d3d8on11 answers with these caps (data/dgvoodoo_caps8.json).
- The occlusion readback's cost on dgVoodoo, measured:
  - one query after 1,600 draws: 3.40 ms;
  - eight: 6.26 ms;
  - eight answered a frame late: 0.18 ms.
  - This measures the asynchronous query section 3 proposes; it does not measure how often the game reads back.
    That stays session 5's figure: 158 in the first minute, none while standing.

**Phase 1: the device (design A, single thread).**
- **Started 14 Oct: kit/d3d8on11, milestone 1 (README there).** The device, swap chain, resources and uploads,
  Clear, Present, Reset, render targets, copies and read-backs, every state the game sets and reads back, and state
  blocks. Recording and execution are already apart, as section 3 recommends. Draws are recorded and counted, not
  executed: milestone 2 is the fixed-function pipeline as shaders. Under Wine, its 22 checks pass through Wine's
  d3d8 and through ours, and a fresh device's 480 states match Wine's except D3DRS_DEBUGMONITORTOKEN,
  D3DRS_POINTSIZE_MAX, and numbers D3D8 does not define.
- **14 Oct: milestone 2, drawing (kit/d3d8on11/d8_ff.cpp).** The fixed-function pipeline as generated shaders:
  - state keys become HLSL, compiled with D3DCompile and cached, with cached D3D11 state objects;
  - fans become lists; ...UP draws go through a ring buffer.
  - 20 scenes, covering the six FVF codes, the states and the stage setups the game's traces show, match Wine's d3d8
    pixel for pixel within 3 of 255.
  - Where the DirectX 8 reference leaves a behaviour open, the code takes Wine's wined3d and names it there. Windows'
    behaviour in those cases is not established.
  - Vertex shaders with code are not drawn (logged). The game never created one in the owner's sessions (section
    2), so this is not a gap in what has been seen.
- Coverage: the subset of section 2. Every method outside it logs and fails, so a missing one is found, not
  guessed.
- How it is checked:
  - Picture comparison with dgVoodoo, frame by frame: the kit's trace_pictures and pictures.py exist.
  - A trace replayer, which does not exist yet: it plays a recorded frame (xikit trace=1, trace_buffers=1) into any
    d3d8.dll. The same frame through dgVoodoo and through ours, compared pixel by pixel offline.
  - Unit tests under Wine in this container: Wine's D3D11 runs here on Mesa's software renderer in a virtual X
    server (xvfb-run; checked with the phase 0 probes). It shows behaviour, not speed.
- Done means: the plaza renders the same as dgVoodoo's output, within the comparison's tolerance, and the frame time
  is measured against dgVoodoo's in the same spot (A/B).

**Phase 2: the command ring (A2 or B, as phase 0 says).** Done means the same pictures, with the game thread's time
in the frame measured against phase 1.
- **14 Oct: built, both designs (kit/d3d8on11, README there).** The D3D8 side and the executor are apart: the D3D8
  side sends a command stream of fixed-width records (d8_proto.h); the executor alone uses D3D11. Three transports,
  chosen in d3d8on11.ini or D8ON11_MODE:
  - `direct`: on the game's thread (phase 1);
  - `thread` (default): a ring read by an executor thread (A2);
  - `remote`: a shared-memory ring read by an executor process, d8x_arm64.exe on an ARM64 machine (B). It presents
    into the game's window, which phase 0's xproc saw work from an ARM64 child on the owner's machine.
- Under Wine, the 22 basic checks pass in all three modes; the 20 scenes match Wine's d3d8, and `thread` and `remote`
  (with the x86 executor) draw exactly what `direct` draws. The frame-capture replay matches its capture.
- Not done: the measurement that defines done (the game thread's time per frame against `direct`, and B against
  A2), on the owner's machine. d8x_arm64.exe has not run anywhere yet.

**Phase 3: game-aware paths,** each a gated fork with its draw change declared (the gate compares everything else),
and each A/B'd in the game. Characters first.

## 5. What exists to build on

- The kit: injection, device and function hooks, the profiler, sampler, traces and A/B. speedfix's levers already
  prototype several of design A's pieces (lazy_state, batching, vs_dedupe, merge_scenes).
- The gate and the tree: 774 of 777 functions verified; forks gated against the game.
- The shader catalogue: every programmable shader's source.
- Captures of SkinAndDrawV2 from the plaza, replayed through the gate (937 of its 1,596 instructions covered).

## 6. Not known yet

- How much of the frame dgVoodoo's translation costs (probe8's next run). The D3D11 runtime's own emulation is
  measured: 1.15 to 1.66 times native per call (phase 0).
- Whether B's cross-process presentation works on Parallels with the game: phase 0's xproc probe saw it work with
  its own windows; d8x_arm64.exe has not run with the game.
- D3D8 behaviour that dgVoodoo reproduces and our device would also have to: the half-pixel offset of pre-transformed
  vertices, fog modes, W-buffering, how D3D8 numbers a strip's flat-shaded colour vertex. Each is to be checked
  against the DirectX 8 SDK's documentation and the picture comparison, not assumed.
- Which of a model's parts are alpha-blended, which bounds the 764 above.
